## 1. Atualizar e testar

Exporte seu workspace em JSON antes de atualizar. Preserve alterações locais; não use `reset --hard`.
Abra o CMD na pasta do projeto (Node 24 LTS recomendado):

```bat
cd launchpad-career
git fetch origin
git switch feat/launchpad-5-4-premium-workspace
git pull --ff-only
set PUBLIC_SUPABASE_URL=
set PUBLIC_PUBLISHABLE_KEY=
set REQUIRE_PUBLIC_AUTH_CONFIG=
npm ci
npx playwright install chromium
npm run build
npm run build:check
npm test
```

Esses `set` limpam somente variáveis nesta janela para os testes determinísticos. Não modificam configurações remotas. Nenhum teste de pagamento cobra dinheiro.

## 2. Gerar NOVA pasta Staging

Depois dos testes, copie somente a chave pública publishable do projeto em Supabase → Project Settings → API Keys. Substitua o exemplo abaixo localmente. Nunca envie service_role, sb_secret, SMTP, senhas, Paddle API/signing secret ou chave de IA para o frontend.

```bat
set PUBLIC_SUPABASE_URL=https://oyatshlhqdxosvbelsvp.supabase.co
set PUBLIC_PUBLISHABLE_KEY=COLE_SOMENTE_A_CHAVE_PUBLICA
npm run build:staging
npm run build:check
```

O build recria `_site`; não reutilize uma pasta antiga. Confira `_site\build-manifest.json`: **71 arquivos** e `publicAuthConfigured: true`; a versão `5.4.0-rc.1` está no `package.json`. Sem chave pública válida, o build Staging falha com segurança. O build padrão sem configuração continua permitindo modo visitante. Se executar testes depois, gere o Staging novamente antes do upload.

**Direct Upload não injeta variáveis do painel em arquivos prontos.** A configuração pública deve estar no build local; `auth-config.js` do código-fonte permanece em branco.

## 5. Roteiro de revisão manual

No modo visitante: adicione candidatura → edite → veja History → altere status no Kanban → veja Calendar → volte Table; filtre e exporte JSON, depois restaure com confirmação. Não use dados pessoais sensíveis em capturas.

No Roadmap: personalize meta, adicione marco e tarefa, filtre por tipo, marque conclusão e recarregue. Em Analytics, compare All records/Last 30 days com as datas das candidaturas: não são tendências de contratação.

Em Settings, navegue pelas oito categorias, salve preferências e altere tema. Em Companies, busque, favorite e abra detalhes/links oficiais. No Coach, valide estado indisponível ou o backend configurado, com consentimento explícito.

**Limites preservados:** histórico de candidatura guarda até 20 atualizações reais, editáveis pelo dono; não é trilha de auditoria de segurança. JSON local aceita até 8 MB, mas limites de nuvem existentes (payload RPC 2 MB e preferências 50 KB) continuam. Um backup local maior pode exigir redução antes de importar na conta; falhas não devem apagar dados existentes. Guest data é local ao navegador e não é isolamento multiusuário.

**Recomendação:** candidato para revisão e testes controlados, após validação do proprietário. NO-GO para clientes pagantes enquanto e-mail real, isolamento publicado, IA/vagas configuradas, compra Sandbox e revisão legal não forem comprovados. Nenhum deploy foi feito nesta entrega.

O workflow herdado do GitHub Pages continua separado: publicação exige execução manual em `main` com `deploy=true`. Push desta branch não satisfaz essa condição. Não execute esse fluxo para publicar Staging na Cloudflare.
