# Launchpad 5.7 — Windows CMD and manual Staging guide

No merge, deploy or secret changes were performed. This guide prepares the existing Cloudflare project, not a new project or a live-charge deployment.

## Update safely

Export JSON from important workspaces first. Save your own code changes before switching branches; never use `git reset --hard` to discard them.

In Windows CMD, from the directory containing your repository (Git + Node 24 installed):

```bat
cd launchpad-career
git status
git fetch origin
git switch feat/launchpad-5.7
git pull --ff-only
set PUBLIC_SUPABASE_URL=
set PUBLIC_PUBLISHABLE_KEY=
set REQUIRE_PUBLIC_AUTH_CONFIG=
npm ci
npx playwright install chromium
npm run build
npm run build:check
npm test
npm run audit:public
```

These `set ...=` commands clear only public build settings in this terminal for deterministic tests. They do not change remote dashboards. If the branch is not local yet, use `git switch --track origin/feat/launchpad-5.7` after fetching. Do not copy private keys or passwords into commands shared with others.

For a local **guest-mode visual preview**, run `npm start` and open `http://127.0.0.1:8000/`. Stop with Ctrl+C. The source preview does not inject build-only Supabase values and is not proof of configured Auth.

## Build a NEW Staging artifact

Use only the public key from your existing Supabase project; never service_role, `sb_secret`, SMTP, Paddle API/signing secret or AI keys.

```bat
set PUBLIC_SUPABASE_URL=https://oyatshlhqdxosvbelsvp.supabase.co
set PUBLIC_PUBLISHABLE_KEY=PASTE_ONLY_YOUR_PUBLIC_PUBLISHABLE_KEY
npm run build:staging
npm run build:check
npm run audit:public
```

The build recreates `_site` from the explicit allowlist. Check `_site\build-manifest.json`: **84 public files**, matching hashes and `publicAuthConfigured: true`. Source `auth-config.js` remains blank. A guest build without public config is useful for local testing but does not connect Auth to your project. If you run the suite again, rebuild Staging before uploading.

Direct Upload cannot inject dashboard variables into files already built locally. The public values must participate in the build. No secret belongs in `_site` or Cloudflare's frontend build settings.

## Publish only after explicit approval

1. Review [release report](../LAUNCHPAD_5_7_RELEASE_REPORT.md) and [before/after gallery](../screenshots/5.7/README.md).
2. Open the existing Cloudflare Pages project **launchpad-career-staging** → Deployments → Create deployment/Upload assets.
3. Upload the **contents of `_site`** with `index.html` at the deployment root. Never upload the full repository, SQL, `.env`, backend functions, tests or `node_modules`.
4. Keep `https://launchpad-career-staging.pages.dev/`. This guide does not authorize publishing the commercial website or real billing.
5. Review DevTools Network for assets/callback failures. Same-origin guest storage remains; different origins need explicit JSON transfer.

GitHub Pages stays separate and unchanged: manual workflow dispatch on reviewed `main`, with **`deploy=true`**, is still required. Pushing this feature branch does not publish the site.

## External configuration remains owner-controlled

- Supabase Email provider and mandatory confirmation; Staging Site URL `https://launchpad-career-staging.pages.dev`; exact redirect `https://launchpad-career-staging.pages.dev/auth/callback.html`. Preserve the approved GitHub Pages callback if still used.
- SMTP/domain authentication, rate limits and real external mailbox confirmation/recovery must be tested. PKCE default links require the original browser; token-hash templates for cross-device flows are in [the 5.6 runbook](5.6-STAGING.md).
- RLS, existing migrations, allowed origins, cloud entitlements and age/consent remain required. Do not reapply migrations or change existing data. New career preference fields use existing private JSON preferences; no new migration or function is needed for 5.7.
- This assumes 5.6 functions have already been deployed. If not, review its handler fixes and manual function deployment instructions in the 5.6 runbook. Uploading frontend files does not update Supabase functions.
- Remotive, AI and Paddle live status was not tested here. Paddle remains Sandbox; do not alter `BILLING_LEGAL_APPROVED`, `BILLING_CHECKOUT_ENABLED`, operator identity, secrets or environment without owner approval.
- Real purchases, portal, plan changes, renewal/failure/cancel, SMTP delivery, second-device sync and published isolation require the [real acceptance checklist](5.6-STAGING.md). Mocks are not proof.

## Backup and rollback

Export JSON per workspace and protect these files as personal data. Only saved content is exported; save resume versions, practice answers and preferences first. New preferences are included in the existing JSON format and restored through explicit confirmation.

Use the prior Cloudflare deployment to roll back frontend assets. The 5.6 code does not expose the new preference editor but existing JSON fields stay intact; retain exports before any edit from an older version. No database rollback is required. Do not restore a whole database over newer customer records automatically.

Before commercial release, verify Supabase backups/PITR and retention for your plan, operator/legal review, support and provider cost monitoring. The release recommendation remains NO-GO for paying customers until real integration gates pass.
