# Launchpad 5.2 — instruções simples para Staging

Esta branch não foi publicada nem mesclada. Não altere credenciais privadas, aprovações legais ou ambiente Paddle para executar estes passos. O projeto existente é **launchpad-career-staging**; não crie outro.

Este refinamento de marca não altera Edge Functions nem migrações. As instruções de backend abaixo continuam sendo as pendências da integração anterior; não republique funções que já estejam atualizadas apenas por causa desta mudança visual.

## 1. Atualizar e testar no Windows CMD

Instale Node.js compatível (usado aqui: 24.19.0), Git e abra CMD na pasta do projeto. Se tiver alterações locais, faça backup antes de trocar de branch; não use comandos de reset destrutivo.

```bat
cd launchpad-career
git fetch origin
git switch feat/launchpad-5-2-commercial-experience
git pull --ff-only
set PUBLIC_SUPABASE_URL=
set PUBLIC_PUBLISHABLE_KEY=
set REQUIRE_PUBLIC_AUTH_CONFIG=
npm ci
npx playwright install chromium
npm run build
npm run build:check
npm test
```

Os comandos `set ...=` acima limpam somente variáveis desta janela CMD para rodar a suíte determinística com configuração padrão, não credenciais do servidor. Não envie senhas, service_role, SMTP ou chaves Paddle para ninguém.

## 2. Gerar uma pasta nova com configuração pública

Em Supabase → Project Settings → API Keys, copie a chave **publishable** pública do projeto correto. Substitua o texto de exemplo abaixo no seu computador. Não copie uma chave secreta. Ela ficará visível no navegador, por definição.

```bat
set PUBLIC_SUPABASE_URL=https://oyatshlhqdxosvbelsvp.supabase.co
set PUBLIC_PUBLISHABLE_KEY=COLE_AQUI_SOMENTE_A_CHAVE_PUBLICA
npm run build:staging
npm run build:check
```

O build recria `_site`; não reutilize uma pasta antiga. O comando staging recusa configuração ausente/inválida. Abra `_site\build-manifest.json` e confirme `publicAuthConfigured: true`. O código-fonte `auth-config.js` continua sem chave; só o artefato recebe os valores públicos. Não execute `npm test` entre esse build final e o upload: os testes geram um artefato próprio. Se executar, gere novamente com `build:staging`.

**Direct Upload não injeta variáveis da Cloudflare em arquivos já compilados.** Configurá-las apenas no painel não corrige um `_site` gerado sem configuração. Em futura integração Git, o build da Cloudflare deverá receber essas mesmas variáveis públicas e `REQUIRE_PUBLIC_AUTH_CONFIG=true`.

## 3. Publicar manualmente, quando aprovar

1. Revise a branch, testes e checklist abaixo. Não faça merge/deploy automático.
2. Cloudflare → Workers & Pages → **launchpad-career-staging** → Create deployment / Upload assets.
3. Envie o **conteúdo** da nova pasta `_site`, com `index.html` na raiz. Não envie repositório, SQL, `.env`, funções ou node_modules.
4. Confirme conscientemente a publicação no projeto Staging existente. Nenhuma alteração em GitHub Pages ou cobranças é necessária.
5. Em `https://launchpad-career-staging.pages.dev/`, confira manifesto e arquivos `/vendor/supabase.js`, `/evolution.js`, `/billing-view.js`, `/styles/evolution.css`, `/assets/career-objects.svg` e `/auth/callback.html` com HTTP 200/MIME correto. O manifesto deve ter 64 arquivos públicos.
6. Para rollback, republique a implantação anterior no painel Cloudflare. Não reverta/apague tabelas nem dados de clientes.

## 4. Supabase — revisão do proprietário

Authentication → URL Configuration:

- Site URL: `https://launchpad-career-staging.pages.dev`
- Redirect URL exata: `https://launchpad-career-staging.pages.dev/auth/callback.html`
- Preserve URLs já necessárias ao GitHub Pages, incluindo `https://theskullguy499-sketch.github.io/launchpad-career/auth/callback.html`; não use curingas amplos.

Authentication → Providers → Email: habilitado, confirmação obrigatória e política de senha revisada. Templates de confirmação/recovery devem usar o link oficial `{{ .ConfirmationURL }}`; não construir token/redirect inseguro manualmente. Revise expiração e limites de envio.

Authentication → Email / SMTP: configure provedor autorizado, host/porta, usuário/senha, remetente de domínio verificado e DNS SPF/DKIM/DMARC conforme o provedor. Segredos ficam somente no painel Supabase. O serviço de envio padrão pode limitar destinatários/taxa; somente mensagem recebida em caixa externa prova entrega. Não foi inspecionado se SMTP está completo.

Não reexecute migrações aplicadas. Revise funções/RLS existentes e teste duas contas reais. Este release não adiciona migração. As atualizações de histórico de cobrança e metadados de vagas exigem publicação revisada somente das funções alteradas. Após revisar o projeto de destino e autenticar a CLI Supabase localmente:

```bat
npx supabase functions deploy billing --project-ref oyatshlhqdxosvbelsvp
npx supabase functions deploy job-explorer --project-ref oyatshlhqdxosvbelsvp
```

Esses comandos publicam backend: execute apenas quando aprovar a atualização Staging. Não alteram secrets por si. Não republique/reset dados ou troque flags para contornar falhas. O webhook existente e sua correção de simulação são preservados.

## 5. Paddle — apenas Sandbox e configuração pendente

O proprietário relata seis secrets existentes; este ambiente não inspecionou seus valores. Revise em Supabase Secrets, sem copiar para frontend: `PADDLE_API_KEY`, `PADDLE_ENVIRONMENT=sandbox`, `PADDLE_CLIENT_TOKEN`, `PADDLE_WEBHOOK_SECRET`, `PADDLE_PRICE_PRO`, `PADDLE_PRICE_PREMIUM`. IDs devem corresponder aos preços recorrentes USD 9/19 do Sandbox, sem impostos inventados.

Revise também `PUBLIC_SITE_URL=https://launchpad-career-staging.pages.dev`, `ALLOWED_ORIGINS` incluindo exatamente essa origem, `BILLING_CHECKOUT_ENABLED`, `BILLING_LEGAL_APPROVED`, `BILLING_TERMS_VERSION`, `BUSINESS_NAME`, `PUBLIC_SUPPORT_EMAIL` e a linha `commercial_settings.enabled`. Não foi possível determinar quais estão ausentes no servidor. Flags de aprovação legal/comercial não foram alteradas: qualquer ativação exige aprovação expressa do proprietário e revisão legal apropriada. Verifique as instruções existentes em [setup comercial](../commercial/SETUP.md).

No Paddle Sandbox, revise domínio/default payment link, client token Sandbox, produtos/preços, endpoint `paddle-webhook`, assinatura e eventos de assinatura/transação. Não troque o segredo já configurado. Métodos disponíveis são apresentados pelo checkout oficial conforme país/moeda/dispositivo/conta/recorrência; não presuma PayPal, Apple Pay, Google Pay ou métodos locais habilitados.

## 6. Roteiro de aceitação real

- Faça backup JSON antes e depois. Verifique que visitante continua separado da conta.
- Adulto autorizado de teste: Create account, aceitar consentimentos, senha/confirmar, receber email externo, confirmar e retornar ao callback. Teste expirado, senha errada e email não confirmado.
- Login, atualizar, logout; recuperar senha via email recebido e definir nova. Nunca compartilhe senha/token. Testar conta A e B em navegadores separados e outro dispositivo; dados de A nunca aparecem em B.
- Criar candidatura/tarefa e sincronizar, exportar/restaurar JSON. Importar dados visitantes somente com confirmação e repetir para verificar ausência de duplicação. Testar exclusão de conta com reautenticação numa conta descartável.
- Buscar vagas via backend, confirmar fonte/data/link, filtros, favoritos/reload/importação e Save to tracker. Campos não fornecidos devem continuar desconhecidos.
- Plans & Billing: plano Free confirmado pelo servidor, usuário adulto elegível e configurações aprovadas. Comprar Pro e Premium separadamente no Sandbox usando apenas cartão oficial de teste do Paddle. Browser success não é prova: conferir assinatura/pagamento no Paddle, evento assinado, banco e plano retornado pelo servidor.
- Testar checkout cancelado, evento duplicado, assinatura inválida, simulação sem concessão, falha/renovação, mudança com cotação, cancelamento/resume, portal e Load provider transactions. Conferir propriedade de cada registro. Jamais habilitar live.
- Testar IA com consentimento e créditos reais somente após configurar backend; indisponibilidade não pode gerar resposta falsa.
- Conferir 375/390/768/1280/1440px, claro/escuro, teclado e leitores de tela/dispositivos reais. Automatização não substitui revisão manual WCAG 2.2 AA.
