# Launchpad 5.3 — guia simples para Windows CMD

## 1. Baixar e validar

Abra CMD dentro da pasta que contém o projeto. Faça backup JSON e preserve alterações locais antes de trocar de branch; não use reset destrutivo.

```bat
cd launchpad-career
git fetch origin
git switch feat/launchpad-5-3-jobs-auth-polish
git pull --ff-only
set PUBLIC_SUPABASE_URL=
set PUBLIC_PUBLISHABLE_KEY=
set REQUIRE_PUBLIC_AUTH_CONFIG=
npm ci
npx playwright install chromium
npm run build
npm run build:check
npm test
```

Os `set ...=` limpam somente estas variáveis públicas nesta janela para executar os testes determinísticos. Não alteram secrets do Supabase ou da Cloudflare. Aqui foram usados Node 24.19.0 e Chromium 154; no Windows, o Playwright instala seu navegador compatível.

## 2. Gerar um novo `_site` conectado

Copie apenas a chave pública publishable do projeto em Supabase → Project Settings → API Keys. Substitua o exemplo no seu computador; não envie credenciais privadas pelo chat. O valor público ficará visível no navegador por definição.

```bat
set PUBLIC_SUPABASE_URL=https://oyatshlhqdxosvbelsvp.supabase.co
set PUBLIC_PUBLISHABLE_KEY=COLE_SOMENTE_A_CHAVE_PUBLICA
npm run build:staging
npm run build:check
```

O comando recria `_site` e recusa configuração pública ausente/inválida. Confira `_site\build-manifest.json`: 67 arquivos e `publicAuthConfigured: true`. O `auth-config.js` do código-fonte permanece sem credenciais. Se executar testes depois desse build, gere novamente o build Staging antes do upload, pois a suíte produz seu próprio artefato.

**Direct Upload não injeta variáveis em arquivos já compilados.** Uma configuração feita só no painel Cloudflare não conecta uma pasta gerada sem os valores públicos. Nunca inclua service_role, sb_secret, senhas, SMTP, Paddle API/signing secrets ou chaves de IA no build/frontend.

## 3. Backend de vagas — somente após sua revisão

Esta versão adiciona descrição da fonte ao `job-explorer`. Não há nova migração nem alteração necessária em billing/paddle-webhook. Depois de revisar a mudança e autenticar a CLI localmente no projeto correto, o proprietário pode publicar apenas essa função:

```bat
npx supabase functions deploy job-explorer --project-ref oyatshlhqdxosvbelsvp
```

Esse comando efetivamente publica backend; não foi executado aqui. Não reexecute migrações nem altere secrets/flags. O bundle inclui o novo arquivo compartilhado de texto. O cache existente tem validade de seis horas e pode continuar servindo registros antigos sem descrição até o próximo refresh normal. Nesse período, o app oferece o link original e informa que a descrição não veio na resposta. Não apague tabelas ou registros para forçar conteúdo.

Revise as origens existentes da função para incluir exatamente `https://launchpad-career-staging.pages.dev`. A chave pública de build também é necessária para o cliente SDK acessar o backend no modo visitante. Sem configuração ou em falha de rede, o aplicativo mantém seus dados e exibe a indisponibilidade, sem inventar vagas.

- Site URL Staging: `https://launchpad-career-staging.pages.dev`

- Preserve o callback existente do GitHub Pages: `https://theskullguy499-sketch.github.io/launchpad-career/auth/callback.html`.

Mantenha provedor Email e confirmação obrigatória habilitados. Use `{{ .ConfirmationURL }}` nos templates oficiais de confirmação/recuperação. Revise política de senha, validade de links e limites de envio.

Se SMTP ainda não estiver configurado: em Authentication → Email/SMTP, configure provedor autorizado, host/porta, usuário/senha, remetente verificado e SPF/DKIM/DMARC conforme o provedor. Secrets ficam somente no painel Supabase. O serviço padrão pode limitar destinatários/taxa. Apenas receber a mensagem em caixa externa e completar o link comprova entrega real. Este ambiente não pôde inspecionar a configuração publicada e não declarou entrega testada.

OAuth não foi configurado nem verificado; não há botões sociais. Configurar OAuth futuramente exige habilitar um provedor real e validar os callbacks antes de exibir o botão.

## 5. Publicar manualmente na Cloudflare existente, quando aprovar

1. Revise a branch, os testes e as capturas.
2. Gere um `_site` novo com configuração pública correta, seguindo a etapa 2.
3. Cloudflare → Workers & Pages → **launchpad-career-staging** → Create deployment / Upload assets.
4. Envie o conteúdo de `_site`, com `index.html` na raiz. Não envie repositório, SQL, `.env`, testes, docs ou node_modules.
5. Confira HTTPS, manifesto e `/jobs-experience.js`, `/styles/opportunities.css`, `/lib/auth-presentation.mjs`, `/vendor/supabase.js` e `/auth/callback.html` com HTTP 200/MIME correto.
6. Teste lista/detalhes, filtros, favoritos e links; no cadastro, receba e confirme o e-mail real antes de validar acesso.

Não crie outro projeto Cloudflare. Para rollback de frontend, restaure a implantação anterior pelo painel; não apague dados nem reverta tabelas. GitHub Pages continua no endereço existente e seu fluxo de publicação continua exigindo aprovação manual `deploy=true` quando aplicável. Não foi acionado.
