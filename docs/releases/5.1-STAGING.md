## Connect the existing Cloudflare Pages staging project

Use Pages project **launchpad-career-staging** only. No production project or
commercial flag is changed by these instructions alone.

1. In Cloudflare, Workers & Pages → launchpad-career-staging → Settings →
   Build & deployments, review the intended source branch
   `feat/launchpad-5-1-premium-commercial`. If using Git integration, selecting a
   branch may enable deployments: perform this action only when ready to publish
   the reviewed staging build. Disable unrelated unattended production publishing.
2. Build command: `npm ci && npm run build`. Output directory: `_site`.
   Root directory: repository root. Node version: `24.19.0`.
3. Settings → Variables and Secrets: configure the environment actually used by
   the desired deployment (Production for the stable pages.dev hostname; Preview
   for branch previews). The values are public build configuration, not passwords:

   | Variable | Value |
   | --- | --- |
   | `NODE_VERSION` | `24.19.0` |
   | `PUBLIC_SUPABASE_URL` | Exact HTTPS root from Supabase Project Settings → Data API |
   | `PUBLIC_PUBLISHABLE_KEY` | Public `sb_publishable_…` key from Project Settings → API Keys |
   | `REQUIRE_PUBLIC_AUTH_CONFIG` | `true` |

4. Never add `service_role`, `sb_secret_`, SMTP, database, Paddle API/signing or
   OpenAI secrets to Pages/frontend variables. Those remain in Supabase server
   secret management. The owner chose direct Cloudflare configuration; no public
   project values were supplied to this task or committed.
5. Rebuild the reviewed commit. Build variables are not automatically injected
   into a static page already deployed. The build writes only `_site/auth-config.js`;
   committed `auth-config.js` remains blank. Missing public configuration now fails
   when required instead of silently publishing a guest-only acceptance site.
6. Open `/auth-config.js` on staging and verify only the two public fields.
   Inspect `build-manifest.json`: `publicAuthConfigured` must be true; record hashes.
   Verify `/premium.js`, `/styles/premium.css`, `/assets/career-ascent.svg` and
   `/vendor/supabase.js` return 200 with correct MIME types. SQL, functions,
   node_modules and documentation must not be present in the public artifact.
7. If using GitHub's **Review and deploy Cloudflare staging** workflow, configure
   environment `cloudflare-staging` with required reviewers, staging variables and
   least-privilege Cloudflare secrets as described in the commercial deployment
   guide. Manually dispatch `approve_staging=true`; it requires public Auth config.
   A workflow must exist on the default branch for GitHub's dispatch UI.

Run from a clean local checkout. Do not paste real credentials into committed files.

The upload is a manual instruction requiring owner approval, not an action this
task performs. `--branch staging` produces a branch preview unless it is the
project's configured production branch. Use the actual preview URL returned by
Cloudflare; do not assume it updates the stable staging hostname. To publish the
stable staging hostname, use the project's configured production branch only
within this dedicated staging project after explicit review. Configure callbacks
for the exact chosen hostname, not a wildcard. `npm test` above runs before public
variables so deterministic browser tests never contact the owner's project.

## Supabase dashboard checklist

- Back up database; inspect which existing migrations and plan seed are applied.
  Apply only unapplied additive migrations. No reset, destructive migration or
  credential rotation is part of this change.
- Auth → URL Configuration: Site URL
  `https://launchpad-career-staging.pages.dev/`; Redirect URL
  `https://launchpad-career-staging.pages.dev/auth/callback.html`.
  Add an exact preview callback only if testing that preview deliberately.
- Auth → Providers → Email: enable signup and **Confirm email**, password minimum
  12; retain rate limits and age/terms onboarding hook. Do not weaken server
  confirmation policy to bypass tests.
- Configure custom SMTP in the Auth email settings, verify sender/domain SPF,
  DKIM and DMARC, and verify the token-hash templates in
  [Supabase setup](../SUPABASE_SETUP.md). SMTP passwords remain server-only.
- Edge Function `ALLOWED_ORIGINS` must contain only intended exact origins;
  `PUBLIC_SITE_URL` must be the chosen staging URL. Preserve intentional Pages
  demo origins separately. Do not add broad preview wildcards.
- Verify both required user-owned tables and commercial RLS/functions with two
  confirmed accounts through publishable credentials, direct REST/RPC attempts,
  account switching, guest import, reload and cross-device synchronization.
- Signup, resend, confirmation, login/logout, recovery/reset and reauthentication
  deletion must each have real dated evidence. A “sent” UI response is not proof
  of mailbox delivery. A failed public config shows guest-mode guidance.
